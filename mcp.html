MCP server

Answerable, from inside your tools.

Scan a site, generate a fix, or read a playbook without leaving Claude or Cursor. Ten tools, the same scanner and data as the website, called directly from an AI assistant.

What this connects

The Answerable MCP server exposes the same scanner, fix generators and playbook content as the website, as ten callable tools instead of a page. Point an MCP client at it and the assistant can run a scan, build a robots.txt or llms.txt file, generate placeholder-safe JSON-LD, or read one of the fourteen vertical playbooks, without a person copying anything between a browser tab and a chat window.

Every tool is read-only and non-destructive. None of them write to your site, send a message, or change an account anywhere. Three tools — scan_site, compare_sites, generate_schema — make an outbound request to the domain you give them, the same as the public scanner. The other five work entirely from this project's own data and fetch nothing external.

Like the scanner itself, every tool measures AI readiness: whether a crawler can reach a page, and whether its signals give a model reason to trust it. None of them measure whether an assistant currently mentions a brand in a live answer — that depends on the prompt, the session and the model's training data, and no tool here can observe or promise it.

Measuring that is a different job. Two tools here, get_citation_prompts and get_citation_sample, hand you the questions and an anonymised sample so you can run a check yourself. Running one for you is the early-access citation tracking report. No tool here queries a model for you.

Connect it

The server speaks MCP over Streamable HTTP at a single URL: https://answerable-app.vercel.app/api/mcp. No API key, no account.

Claude Code (CLI)

Run once, from any directory:

Terminal 
claude mcp add --transport http answerable https://answerable-app.vercel.app/api/mcp

Claude Desktop, or any JSON-config MCP client

Add this to the client's MCP config file (for Claude Desktop, claude_desktop_config.json):

claude_desktop_config.json 
{
  "mcpServers": {
    "answerable": {
      "url": "https://answerable-app.vercel.app/api/mcp"
    }
  }
}

Cursor

Add the same shape to .cursor/mcp.json (project) or ~/.cursor/mcp.json (global):

.cursor/mcp.json 
{
  "mcpServers": {
    "answerable": {
      "url": "https://answerable-app.vercel.app/api/mcp"
    }
  }
}

Restart the client, or reload its MCP connections, then ask it to scan a domain, compare two sites, or pull up a playbook.

The server supports MCP protocol versions 2026-07-28, 2025-11-25 and 2025-06-18. Every request must send an MCP-Protocol-Version header; a request without one returns 400. Clients add it automatically. If you call the endpoint by hand, send that header. For 2026-07-28 you also need the _meta protocol fields and the Mcp-Method and Mcp-Name headers.

Ten tools

Each one below shows what it needs, what it fetches, and one real example call and response.

Scanning

scan_site

Fetches: the live domain · Needs: domain (bare hostname, e.g. example.com)

Scans a domain's public robots.txt, llms.txt, sitemap declaration and homepage, and scores it out of 100 across three pillars: discoverability, technical foundation, and content & trust. Returns the score, the three pillar scores, access state for the 10 tracked AI crawlers, every failed check with its fix, and how the score compares to Answerable's own benchmark data. If the site looks like a store, it also reports a separate commerce sub-score: the UCP endpoint, one product page's schema, and the llms.txt authorship result. That sub-score is never part of the 100.

Example call
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": { "name": "scan_site", "arguments": { "domain": "example.com" } }
}
Example response (trimmed)
AI readiness scan — example.com

Score: 29/100
  Discoverability:      26/40
  Technical foundation: 3/20
  Content & trust:      0/40

That's 44 points below the average of the 219 sites we've scanned (73/100).

AI crawler access: 10/10 open.

Failed checks, highest point value first:
  - Organization / WebSite schema (0/8 pts): Add Organization schema — Defines your brand as a verifiable entity — the base layer of trust.
  - Author / about signals (0/8 pts): Add an about page and author information — AI systems weigh source credibility through ownership signals.
  - Contact signals (0/8 pts): Add a contact page or email link — Reachability is a baseline trust marker.

Passed: AI crawler access (10/10 open), Page title.

Fixes

generate_schema

Fetches: the live domain's homepage · Needs: domain, type (organization, faqpage, article, product or localbusiness)

Fetches a domain's homepage for its real title, meta description and declared language, then returns ready-to-paste JSON-LD of the requested type. Fields the scan cannot know — a FAQ's actual questions, a product's real price — come back as clearly bracketed placeholders, never invented values.

Example call
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": { "name": "generate_schema", "arguments": { "domain": "example.com", "type": "organization" } }
}
Example response
Organization and WebSite JSON-LD for example.com, ready to paste inside a <script type="application/ld+json"> tag in the page's <head>:

{
  "@context": "https://schema.org",
  "@graph": [
    {
      "@type": "Organization",
      "name": "[Your company name]",
      "url": "https://example.com",
      "description": "[A one-sentence description of your business]"
    },
    {
      "@type": "WebSite",
      "name": "Example Domain",
      "url": "https://example.com",
      "inLanguage": "[e.g. en]"
    }
  ]
}

generate_robots_txt

Fetches: nothing · Needs: allow and/or block (arrays of tracked crawler names), optional sitemap_url

Builds a robots.txt file that explicitly allows or blocks named AI crawlers from the tracked list of 10, plus an optional Sitemap line. Call list_ai_crawlers first for the exact tracked names.

Example call
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "generate_robots_txt",
    "arguments": {
      "allow": ["GPTBot", "ClaudeBot", "PerplexityBot"],
      "block": ["Bytespider", "CCBot"],
      "sitemap_url": "https://example.com/sitemap.xml"
    }
  }
}
Example response

User-agent: ClaudeBot
Allow: /

User-agent: PerplexityBot
Allow: /

Disallow: /

Sitemap: https://example.com/sitemap.xml

generate_llms_txt

Fetches: nothing · Needs: name, description, optional key_pages (array of url + description)

Builds an llms.txt file — the emerging convention that gives AI systems a curated map of a site — from a name, a one-sentence description and a list of key pages.

Example call
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "generate_llms_txt",
    "arguments": {
      "name": "Example Co",
      "description": "A sample company used for documentation.",
      "key_pages": [
        { "url": "https://example.com/pricing", "description": "Plans and pricing" },
        { "url": "https://example.com/docs", "description": "Product documentation" }
      ]
    }
  }
}
Example response
llms.txt — paste this at your site root (e.g. https://yoursite.com/llms.txt):

# Example Co

> A sample company used for documentation.

## Pages
- [Plans and pricing](https://example.com/pricing)
- [Product documentation](https://example.com/docs)

Citation tracking

get_citation_prompts

Fetches: nothing · Needs: vertical (a vertical slug, e.g. crm)

Returns the buying-intent questions Answerable uses to test whether an assistant names a brand, for one vertical, plus a short protocol a person can run in their own assistant: ask each question in a separate conversation three to five times, note whether the brand is named and whether it appears in a heading, list label, table or bold text, and judge the spread rather than one answer. The questions don’t name any brand in the category being measured. A few mention an integration platform such as Slack or Google Workspace, because that is how buyers ask. Read from this project’s own question files. A vertical with no questions yet returns a message that names the verticals that have them.

How to run this yourself, in any assistant you have access to:
1. Pick one assistant and one model, and note its name and today’s date.
2. Ask each question in a separate, new conversation. Do not reuse a chat: earlier answers change later ones.
3. Ask every question three to five times, each time in a new conversation.
4. For each answer, note two things: whether your brand is named at all, and whether it appears in a heading, list label, table or bold text (featured) rather than only in running prose (named only).
5. Judge the spread, not one answer. A question where you are named in some tries and not others is unstable. One where you are never named is a gap. A single answer is not a finding.

Keep the limits in view: the result describes one assistant on one date. It is not a ranking, it says nothing about other assistants, and it is not a forecast of traffic. Answers move with phrasing and over time.

Why there is no tool that runs the check

A run asks a model about 90 questions in total, at about five seconds each. That is far past this server’s time limit, and it would spend a model quota that nothing stops a stranger from draining. So the tools hand you the questions and the protocol, and you run them in your own assistant. If you want us to run it for you, that is the early-access citation tracking report.

Errors are specific

Calling generate_schema with an invalid type returns: "type" must be one of: organization, faqpage, article, product (got "invalid"). Calling a tool name the server doesn't recognize returns a JSON-RPC error naming it, with the full tool list. Nothing fails silently or returns a generic message.

Privacy

The same rule as the public scanner applies here: nothing is stored about who calls a tool.

The three tools that scan a live domain — scan_site, compare_sites, generate_schema — fetch directly from that domain, the same way the public scanner does. Scanning a store can also read one product page, only where robots.txt allows it. They don't route through a third-party proxy, and the fetched content is used only to build the response handed back to the calling tool. It isn't logged or retained anywhere.

To enforce the same rate limit the public scanner uses, the server keeps a one-way hash of the caller's IP address paired with a request counter. It expires automatically within a day, isn't linked to which domain was scanned or which tool was called, and the raw IP address is never stored. No other identifying information is recorded: no client name, no API key, no account, no log of individual tool calls.
