# The State of AI Readiness report (gated PDF)

What it is, where everything lives, what is stored, the limits, how to run it, how to replace the PDF, and the way back. Built 11 October 2026.
Read this before touching `lib/readiness*.js`, `content/readiness.json`, `research/state-of-ai-readiness.html`, `report-signup.js`, or the report card.

## What a visitor sees

1. **The homepage report card** (`report-card.js`, a `<template id="rcTemplate">` in `index.html`). A small card, bottom right on a wide screen, a slim bar along the bottom under 700 px. It appears once per browser session, after 40% scroll or 15 visible seconds, whichever comes first, never while the scan's "Analyzing" screen runs. Escape and a visible close button remove it. It takes no focus. Dismissal is kept in `sessionStorage` inside try/catch (no cookie). It runs on the homepage only, and checks the path again: never on `/pro`, `/privacy`, `/r/*`, `/pro/*`, a report page or the report page itself.
2. **The page** `/research/state-of-ai-readiness` (indexable; generated by `scripts/generate-readiness.js` from `content/readiness.json`): four findings with their scan dates, how it was measured, what it does not show, and the form.
3. **The form** (`report-signup.js` posts to `/api/readiness`): email, a required box "Send me the report", a separate optional unticked box "Also send occasional Citehound updates", a hidden honeypot. The answer is the same words whether or not the address was known.
4. **The email** (`lib/readiness-mail.js`): a signed link to the PDF, valid 30 days, no address in it, a "Remove my address" link and the List-Unsubscribe headers. No attachment, no tracking pixel, no tracked links.
5. **The download** `/readiness/download/<72 hex>`: the PDF, streamed from the database, with `noindex`, no referrer, `no-store`.
6. **Removal** `/readiness/remove/<64 hex>`: a page with one button; a POST deletes the record (also the mail client's one-click POST).

## Where the PDF is, and where it is not

It is **only in the database** (Upstash Redis, the same database as Pro), key `sr:pdf` (base64) with `sr:pdf:meta` (sha256, bytes, name, date). It is never a file in the repository or in a served path:
`*.pdf` is in `.gitignore`, `scripts/test-readiness.js` and `scripts/test-static-exposure.js` fail if a PDF is tracked or sits anywhere in the tree, and the live smoke checks six guessable addresses (all 404). The function reads it from the database, checks it against its hash, and sends it only to a valid signed link. A stored copy that does not match its hash is never served.

Size: the Upstash free plan takes requests up to 1 MB; the report is 284,311 bytes (about 379 KB as base64). The store refuses anything over 650,000 bytes. Uploaded to production on 11 October 2026 and read back with a matching hash.

### Replace or delete the PDF

```bash
node scripts/pro-admin.js readiness-upload /path/to/new-report.pdf     # checks it is a PDF under 650 KB, stores it, prints the sha256
shasum -a 256 /path/to/new-report.pdf                                   # compare with the hash it printed
node scripts/pro-admin.js readiness-info                                # name, size, hash, integrity, switch, number of addresses, last 7 days
node scripts/pro-admin.js readiness-pdf-delete --yes                    # remove it (without --yes it only says what it would do)
```

Before a new PDF goes out, check its numbers: extract the text page by page (see the header of `scripts/verify-readiness-pdf.js`) and run
`node scripts/verify-readiness-pdf.js local/launch-report/stats.json <folder with p1.txt ... p8.txt>`. The Launch Edition (8 pages, sha256 `ee5438d5…ed0b1b2`) was checked on 11 October 2026: 68 figures, 0 mismatches, all from the July snapshot (219 scored of 278 attempted), none from the 2 October rescan. `scripts/test-readiness-figures.js` re-checks every figure on the public page against `stats.json` whenever that file exists.

## The switch

`node scripts/pro-admin.js readiness off` closes signups and downloads at once (no redeploy): the form says the report is not available and every download link answers 503. `readiness on` opens them again. With no PDF stored the report is closed too. Nothing needs an environment variable.

## What is stored (and what the privacy page says)

| Key | What | How long |
|---|---|---|
| `sr:e:<id>` | email, createdAt, consentVersion, updates ("0" or "1") | 12 months |
| `sr:index` | the ids, so the owner can export | 12 months + 30 days |
| `sr:n:<id>:<day>` | report emails sent to that address that UTC day | 2 days |
| `sr:cap:<day>` | report emails sent that UTC day | 2 days |
| `sr:off` | the switch | until changed |
| `sr:pdf`, `sr:pdf:meta` | the PDF | until replaced |
| `pro:stats:<day>` fields `readiness_*` | daily totals only | 400 days |

`<id>` is HMAC-SHA256(`PRO_HASH_SECRET`, `"sr-id|" + address`): a different label from the Pro waitlist, so the two lists cannot be joined. The list is separate from the Pro waitlist, and removing from one leaves the other alone. Nothing logs an address or a token.

## Limits

- Six accepted signups an hour per network (`LIMITS.readinessjoin`), a flood guard of 60 POSTs an hour (`LIMITS.readiness`), 30 downloads an hour (`LIMITS.readinessdl`).
- Three report emails a day per address (`R.PER_ADDRESS_PER_DAY`), and a daily cap for all addresses (default 300; optional `READINESS_EMAIL_DAILY_CAP`). A throttled request gets the same answer and is counted as `readiness_throttled`.
- A download link works 30 days (`R.LINK_SECONDS`) and only while its record exists, so a removal revokes it. A link to a record that is gone is the generic "not valid" page; an expired genuine link says it has expired and offers a new one.
- Without `PRO_HASH_SECRET` the whole feature answers 503 (fail closed), like every Pro endpoint.

## The owner's commands

```bash
node scripts/pro-admin.js readiness-info                          # the state of the report
node scripts/pro-admin.js readiness on|off                        # switch
node scripts/pro-admin.js readiness-export > readers.csv          # email, createdAt, consentVersion, updates (personal data: readers*.csv is in .gitignore; never commit it)
node scripts/pro-admin.js readiness-remove name@example.com       # says what it would do
node scripts/pro-admin.js readiness-remove name@example.com --yes # removes that address (found by its own address, no secret needed)
node scripts/pro-admin.js stats --days 7                          # includes the readiness_* counters
node scripts/pro-admin.js health                                  # includes a "Report list" line
```

The second box (updates) is stored and exported. **Nothing sends updates yet.** If you ever send any, send only to rows with `updates` = yes, with a removal link, and say so in `/privacy` first.

## Honest framing

Everything on the page and in the email says "readiness", names no scanned site, makes no causal claim and says what the report does not show. `scripts/generate-readiness.js --check` fails on a banned word, a promise, a price, or a missing figure.
